Measured 2026-09-26 on a Mac mini (M2 Pro) under Asahi Linux, aarch64, 16K
pages, PipeWire. Release build, librespot 0.8.0. The x86_64 run is still to
do.

## What changed along the way

- **Pause latency was 197 ms p50 / 290 ms p99 with librespot's own
  PulseAudio sink.** Its `stop()` calls `drain()`, which blocks until the
  whole server buffer has played, so you *hear* the pause ~200 ms late. The
  daemon now uses its own sink (`sink.rs`): `flush()` instead of `drain()`,
  a 60 ms server buffer, and a named stream ("omarchy-rust-spotify") in the
  mixer. Result: p50 36 ms, p99 117 ms.
- **The player thread only reads commands between packets**, and it can be
  blocked in `write()` on a full buffer. The daemon now fires a deadline-based
  interrupt before commands that cut the audio (pause, skip, seek), and the
  sink abandons the in-flight write within ~5 ms. Result: p50 25–29 ms, p99
  75 ms (40 commands) / 121 ms (60 commands).
- **librespot's `SessionConnected`/`SessionDisconnected` mean "this Connect
  device was activated/deactivated"**, not "the session connected". The
  reducer treats them as `active`; `connected` comes from Spirc starting.
- **`Spirc::activate()` does not take over playback; `Spirc::transfer(None)`
  does**, and only while the device isn't already active.
- **RSS was 47 MB, of which ~20 MB was glibc malloc arenas**: glibc gives
  each allocating thread its own arena and keeps the pages. `main` now calls
  `mallopt(M_ARENA_MAX, 2)` before any thread starts and Tokio runs 2 workers
  instead of one per core: 25 MB while playing, 18 threads, same latency.
- **Build:** librespot-core 0.8.0's build script fails with vergen 9.1 (it
  pairs `vergen-gitcl` 1.0.8 with an incompatible `vergen-lib`). Pinned
  `vergen = 9.0.6` in `Cargo.lock`.

## Open items

- **Command → event outliers (~2 in 60 over 100 ms, max 294 ms).**
  Hypothesis, not verified: Spirc handles commands sequentially and awaits a
  network PUT of the Connect state after each one, so a command that arrives
  mid-PUT waits for it. Next step: trace Spirc timing; if confirmed, reflect
  the command in the UI optimistically and reconcile on the event.
- **Transfer needs live playback on the account.** If Spotify's cluster has
  no active device (e.g. playback went stale), a transfer carries an empty
  state ("current track couldn't be resolved"). M1 should fall back to
  starting the last context.
- **Sign-in:** credentials are imported from spotify-player's
  `credentials.json`; in-daemon OAuth is M1.
- **MPRIS bus name** is `org.mpris.MediaPlayer2.omarchy_rust_spotify`
  (underscores; the plan's hyphenated form is legal but less common).

## Go / no-go

**Go.** librespot 0.8 exposes everything the design needs (every control on
`Spirc`, push events for track, status, seek, shuffle, repeat and volume),
playback and MPRIS work on Asahi, the event paths are two to three orders of
magnitude inside budget, and QML can use the protocol directly. Queue editing
still needs an unreleased librespot (risk R2); nothing in M1–M3 depends on
it.

## Reproduce

```sh
cargo build --release
target/release/omarchy-rust-spotifyd &          # imports spotify-player's login on first run
target/release/omarchy-rust-spotify cmd play    # take over the account's current playback
target/release/omarchy-rust-spotify debug roundtrip 40
target/release/omarchy-rust-spotify debug latency 50   # in another terminal, while controlling playback
quickshell -p spikes/qml-socket
```
